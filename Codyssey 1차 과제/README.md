# I. 개요

## 1. 배경

생성형 AI는 이메일 초안 작성과 같은 반복적인 문서 업무를 빠르게 지원할 수 있다. 그러나 같은 요청을 입력하더라도 모델에 따라 입력 정보의 반영 정도, 말투, 이메일 형식, 확인되지 않은 내용의 추가 여부에서 차이가 발생한다. 따라서 실제 업무 자동화에 사용할 모델을 선정하기 위해 동일한 협업 요청 메일 작성 과업을 세 가지 LLM에 수행시키고 결과를 비교하였다.

## 2. 목적

본 비교의 목적은 같은 학과 동기들에게 일축압축 실험 참여를 요청하는 이메일 작성 과업에서 가장 적합한 LLM을 선정하는 것이다. 각 모델이 사용자가 제공한 정보를 정확하게 반영하는지, 요청 목적을 명확히 전달하는지, 수신자에게 적절한 말투와 이메일 형식을 사용하는지를 평가하였다. 선정된 모델은 이후 시스템 프롬프트 설계, Few-shot 적용 및 V1→V2 개선 과정에 사용한다.

## 2. 선정 이유

Claude Opus 4.8은 사용자가 제공한 실험명, 수신 대상, 날짜, 시간 및 최소 인원을 빠짐없이 반영했으며 제목과 본문을 가장 체계적으로 구성하였다. 특히 입력에 없는 장소, 회신 기한 및 발신자 정보는 구체적인 값을 임의로 생성하지 않고 빈칸으로 표시하여 세 모델 중 확인되지 않은 사실을 추가할 가능성이 가장 낮았다.

또한 같은 학과 동기에게 적합한 정중하면서도 친근한 말투를 사용하고, 참여 요청과 회신 행동을 명확하게 전달하였다. 여러 빈칸을 사용자가 직접 수정해야 한다는 단점은 있지만, Gemini 3.1 Pro의 확인되지 않은 개인 업무 수행 약속 추가와 ChatGPT 5.6 Sol의 제목 및 수신자 맞춤성 부족을 고려하면 정확성, 말투 및 형식의 균형이 가장 우수하다.

따라서 본 과제의 팀 협업 요청 메일 작성 자동화에 사용할 최종 모델로 Claude Opus 4.8을 선정하였다.

# 1. 시스템 개요

| 항목 | 내용 |
| --- | --- |
| **과업명** | **공적인 협조 요청 글 작성** |
| **최종 모델** | Claude Opus 4.8 |
| **실행 환경** | API |

## 1.1 타겟 사용자

팀원, 학과 동기, 조교, 교수, 다른 부서 또는 외부 협력사에게 참여·자료·검토·일정 조율·협조 등을 요청하는 메일을 작성해야 하는 대학생 및 실무자를 대상으로 한다. 특히 상대방과의 관계에 맞는 말투를 선택하거나, 요청에 필요한 정보를 빠짐없이 정리하는 데 어려움을 느끼는 사용자를 주요 대상으로 설정하였다.

## 1.2 업무 문제

협업 요청 메일은 같은 내용이라도 수신자가 동기인지, 교수인지, 외부 협력사인지에 따라 표현이 달라져야 한다. 또한 목적, 요청 사항, 일정, 회신 방법 등이 누락되면 실제로 사용하기 어려운 메일이 만들어질 수 있다. 일반적인 LLM은 부족한 이름·날짜·장소를 임의로 채우거나, 확인되지 않은 업무 수행을 사용자를 대신해 약속할 가능성도 있다. 따라서 입력 정보의 충분성을 먼저 판단하고, 필요한 경우 질문한 뒤 관계와 상황에 맞는 메일을 작성하도록 시스템을 설계하였다.

# 5. Few-shot

```
case 1) 발신자 정보, 수신자, 목적, 요청 사항, 기한이 모두 명확히 주어진 경우
→ 확인 질문 없이 바로 메일 제목과 본문을 출력한다.

case 2) 수신자의 성함이나 소속처럼 메일에 반드시 들어가야 할 핵심 정보가 빠진 경우
→ “교수님”, “조교님”처럼 임의로 채우지 않고 반드시 먼저 질문한다.

case 3) 수신자와의 관계에 따라 톤을 다르게 조절한다.
- 동기: 친근하지만 정중하게, 이모지나 과도한 캐주얼 표현은 사용하지 않는다.
- 조교/교수: 격식 있는 존댓말과 완곡한 표현을 사용한다.
- 외부 협력사: 공식 문서체를 사용하고 회사명·직함을 정확히 명시한다.

case 4) 회신 기한이 입력에 없는 경우
→ 임의로 날짜를 만들지 않고 “가능하신 범위 내에서 편하신 때”처럼 표현하거나, 일정 시작일을 기준으로 합리적인 회신 기한을 제안한다.
```

# 6. 환각 검증

환각 검증은 4.2의 V1 테스트에서 생성한 네 가지 메일을 기준 자료로 사용하였다. 교수 성함, 요청 자료, 참여 인원, 회신 기한, 수신자 유형을 다시 질문하여 모델이 이전 정보를 임의로 만들거나 이미 제공된 정보를 잃어버리는지 총 5회 확인하였다.

## 6.3 검증 3｜동기 참여 인원과 외부 현장 담당자 인원 비교


# 7. 시스템 프롬프트 V2 설계

V1 테스트와 환각 검증에서 확인된 문제를 기준으로 필요한 보완 규칙을 정리하고, 이를 반영한 V2를 설계하였다. V2에는 Few-shot, 관계별 톤 기준, 이전 대화 재확인 규칙과 단계적 수행 절차를 함께 적용하였다.

## 7.1 V2 설계 방향

V1에서는 장소나 회신 기한이 빠진 경우에도 메일을 먼저 작성한 뒤 누락 사실을 안내했으며, 외부 협력사 메일에는 입력하지 않은 **“2025년”**이 추가되었다. 또한 환각 검증에서는 세부 정보를 확인할 수 없을 때 이를 인정하고 확인 절차를 제안하는 대응은 적절했지만, 앞서 제공된 회신 기한을 찾지 못하고 모두 없다고 판단하는 정보 소실형 오류가 확인되었다.

이에 V2는 핵심 정보가 부족하면 최대 3개의 질문을 먼저 제시하고, 답변을 받기 전에는 최종 메일을 작성하지 않도록 설계하였다. 또한 입력된 정보만 사용하고 이전 대화를 다시 확인하도록 하였으며, 수신자 관계에 맞는 말투와 본문 이모지 금지 규칙을 적용해 출력의 정확성과 일관성을 높이고자 하였다.

## 7.2 단계적 수행 절차

1. 발신자 정보, 목적, 수신자와의 관계를 고려해 제목과 인사말을 선정한다.
2. 요청 사항과 기한·일정을 참고해 본론 내용을 정리한다.
3. 원하는 톤과 수신자 관계에 맞게 표현을 수정한다.
4. 부족한 정보가 있다면 최대 3개의 확인 질문을 제시하고, **사용자의 답변을 받기 전까지 최종 출력을 진행하지 않는다.**
5. 정보가 모두 확인된 후에만 제목과 본문으로 구분된 최종 메일을 출력한다.

## 7.3 V2 검증 결과

회신 기한, 회신 방법, 실험 장소가 제공되지 않은 일축압축 실험 참여 요청으로 V2를 검증하였다. V2는 누락된 세 가지 정보를 질문한 뒤 사용자의 답변을 기다렸으며, 답변을 받은 후에만 **8월 15일**, **카카오톡 개인 메시지**, **지진방재연구 실험실**을 반영한 최종 메일을 작성하였다. 이를 통해 임의의 값을 생성하지 않고 질문과 최종 출력이 분리되는 것을 확인하였다.

| 출력 범위 준수 | 제목과 본문 외에도 누락 정보 안내와 추가 수정 제안을 함께 출력했다. | 제목과 본문 외에도 작성 완료 안내와 톤 조정 제안을 함께 출력하여, 최종 결과만 출력하는 형식은 완전히 지키지 못했다. |

8.1과 8.2의 실제 출력만 비교하면, V2의 핵심 개선점은 **임의 값 생성 방지 자체가 아니라 누락 정보를 먼저 질문하여 최종 메일의 완성도를 높인 것**이다. 반면 제목·본문 외의 부가 설명과 이모지는 V2에서도 일부 남아 있어 추가 보완이 필요한 부분으로 확인되었다.
